# Agent 开发工作台需求文档

- 版本：V0.1
- 日期：2026-10-24
- 状态：需求基线草案，可据此开展整体设计
- 来源：开发者提供的实际开发流程及本次对话中整理的需求
- 默认范围：个人使用、优先本地或单台开发服务器部署，以 OpenCode 为主要执行工具

## 1. 背景与目标

开发者是一名后端工程师，新接手多个项目，对业务和代码尚在熟悉中。目前使用 OpenCode 开发，并使用 Superpowers 组织开发过程。需求需要经过代码分析、范围确认、开发、多模型评审、人工自审、概要设计评审、测试准备及反馈处理。

多个需求同时推进时，需要将代码复制到 Docker 环境独立开发。开发者负责准备 Dockerfile、Agent 配置、容器配置及挂载内容，希望环境尽量接近本机，并在明确隔离边界内给予 Agent 足够执行权限。

系统目标：每个需求拥有独立工作区，按照可配置流程调用 Agent，并持续保存需求、代码、决策、评审、文档及测试反馈之间的对应关系。

## 2. 角色与范围

| 角色 | 职责 |
| --- | --- |
| 开发者 | 接收需求、确认范围、配置环境、运行 Agent、自审代码、处理反馈、导出交付物 |
| 主管或评审人 | 审查概要设计，提出意见并确认结果 |
| 测试人员 | 执行测试，反馈问题并确认修复 |
| Agent | 分析、制定计划、开发、评审、生成材料和修复问题 |

第一版以开发者单人操作为主。主管评审及测试反馈可通过导出文档、手工录入结论完成。第一版交付终点为代码及配套材料达到可交付状态，不包含自动合并和生产部署。

## 3. 核心业务对象

| 对象 | 定义 |
| --- | --- |
| 需求 | 业务开发任务，包含目标、范围、验收标准和版本历史 |
| 项目 | 一个代码仓库或可独立开发的服务 |
| 需求工作区 | 某需求的项目代码、环境、Agent 会话和产物集合 |
| 项目工作区 | 需求中某一个项目的独立代码副本、分支和环境 |
| 流程模板 | 步骤、依赖、Agent 分工、输入输出及人工确认点 |
| 执行记录 | 某个步骤的一次尝试，保存输入、日志、结果及失败原因 |
| 产物 | 分析报告、开发计划、代码差异、评审、设计及测试材料 |
| 问题单 | 评审问题、测试 Bug、需求变更或架构设计变更 |
| 代码基线 | 代码提交版本以及必要的未提交差异和未跟踪文件清单 |

一个需求可以涉及多个项目；同一项目可以同时属于多个需求，各需求使用独立代码副本及运行环境。

## 4. 业务流程

| 阶段 | 工作 | 产出与通过条件 |
| --- | --- | --- |
| 需求接收 | 录入需求背景、原始描述、附件、约束和验收标准 | 需求说明，缺失信息单列 |
| 全景分析 | 结合代码分析入口、调用链、项目、接口、数据及依赖 | 影响分析报告，标注依据和不确定项 |
| 范围与方案确认 | 确认涉及项目、边界、技术方向和风险 | 开发者确认 |
| Superpowers 开发 | 根据实际配置完成方案细化、任务拆分、实现及验证 | 开发任务和验证结果 |
| 多模型代码评审 | 由不同于开发阶段的模型检查实现 | 评审问题完成处理，必要时复审 |
| 开发者自审 | 查看差异、解释、评审意见和验证结果 | 人工通过或退回 |
| 概要设计生成 | 根据需求和实际代码生成服务端概要设计 | 文档与实现一致，未知内容明确标记 |
| 主管评审 | 导出概要设计并记录审查结果 | 通过或进入变更处理 |
| 测试准备 | 生成测试单及必要的性能测试单 | 覆盖验收标准，前提和指标明确 |
| 测试反馈 | 记录测试执行，处理 Bug、需求及架构变更 | 修复、复评、复测并更新相关材料 |
| 交付归档 | 汇总代码、文档、验证和遗留问题 | 形成可追溯的交付清单 |

概要设计按上述实际流程在开发后生成。对于预先识别的重大架构调整，支持在开发前增加方案评审。Superpowers 的实际步骤及调用方式以用户配置和安装版本为准。

## 5. 功能需求

### FR-01 需求与项目管理

- 创建、编辑、暂停、恢复、归档需求，记录优先级、约束和验收标准。
- 保存需求版本及变更原因，历史版本不可覆盖。
- 登记仓库、技术栈、分支、启动命令、依赖服务和已有文档。
- 沉淀人工确认的项目和业务知识，区分事实、Agent 推断及待确认事项。

### FR-02 全景分析与范围确认

- 从项目目录中确定候选项目，结合授权的代码进行分析。
- 列出业务入口、涉及模块、调用关系、接口、数据表、消息及外部依赖。
- 给出各项目预计改动、兼容性、迁移、性能及历史行为风险。
- 判断引用文件、符号或接口作为依据，并注明分析时的代码基线。
- 未找到实现或缺少上下文时明确说明，不能把推测作为确定结论。
- 开发前确认涉及项目及改动范围；新增项目时重新确认范围。

### FR-03 流程与 Agent 执行

- 提供 Agent CLI 配置管理界面，支持内置 OpenCode 和兼容封装；保存命令、超时、版本检查与凭据变量名，维护不可变配置版本。
- 支持新工作区默认选择及项目覆盖，在准备工作区时固定；切换默认或编辑配置不影响已准备需求。兼容契约与当前边界见 [封装 CLI 接入](26-agent-cli.md)。

- 提供默认流程，允许配置步骤启停、参数、模型、提示词、输入输出及通过条件。
- 支持顺序、并行、条件步骤和人工确认。
- 传递有效产物、版本信息及人工决策，保存实际执行输入。
- 展示状态、日志、产物、耗时、失败原因和等待人工处理原因。
- 支持取消、重试、重新运行；暂停及恢复能力以执行工具能力为准。
- 设置超时、并发上限和最大自动修复轮数。
- 保存 OpenCode 会话关联；恢复原会话的能力需技术验证。
- 支持进入需求环境人工操作并记录处理结果。
- 日常容器内开发操作按已有授权执行；业务确认点与工具权限分别配置。

### FR-04 多需求和跨项目协同

- 每个需求独立保存代码、分支、容器、可写数据、端口、会话、日志和产物。
- 跨项目任务支持依赖关系、独立执行、整体进度和阻塞原因汇总。
- 联调记录参与项目版本及接口约定。
- 必要项目和检查未完成时，不得判定整个需求完成。
- 支持比较目标分支与需求分支，基线更新后重新验证。

### FR-05 Docker 环境管理

- 提供独立的 Docker 镜像与容器管理导航页，集中维护 Dockerfile 版本、镜像列表及构建/拉取/移除记录。
- 集中展示各需求的容器状态、镜像、资源与挂载配置，支持工作区创建、预检、启动、停止、日志及状态核实；复用需求隔离与持久化规则。
- 站点试用应明确标识示例与真实执行；Docker 宿主能力由本机 Runner 提供。当前实现及构建上下文限制见 [Docker 管理说明](24-docker-management.md)。

| 配置类别 | 内容 |
| --- | --- |
| 构建 | Dockerfile、构建上下文、基础环境、工具及版本 |
| Agent | OpenCode、Superpowers、模型和工具配置 |
| 源码 | 仓库或本地目录、分支、提交及可选未提交改动 |
| 启动 | 工作目录、启动命令、依赖服务及健康检查 |
| 挂载 | 必要目录、目标路径、读写方式和用途 |
| 配置 | 普通环境变量与敏感配置引用 |
| 网络 | 需求内部网络、访问策略及宿主机端口 |
| 资源 | CPU、内存、进程数、存储监控及并发限制 |
| 保留 | 代码、日志、运行数据和产物的保留策略 |

- 按指定代码基线创建独立副本，不能默认写回原始目录。
- 纳入本地未提交改动时明确记录，包含必要的未跟踪源码；排除敏感文件和无关生成目录。
- 支持构建、启动、停止、重建和清理，初始化失败可定位具体阶段。
- 容器重建后保留需求代码和必要产物，区分重建环境与删除工作区数据。
- 数据库、缓存、消息队列等可写状态按需求隔离。
- 记录镜像摘要、配置版本、工具版本和源代码基线。
- 尽量保持本机工具和依赖一致，对操作系统、架构和本机专有服务差异明确记录。

权限边界：Agent 可在授权的需求环境内自主执行开发操作。默认不向 Agent 容器提供 Docker Socket、特权模式、宿主机根目录或其他需求目录。挂载和网络访问由明确配置决定。Docker 共享宿主机内核，不能等同于完整的宿主机安全沙箱。

### FR-06 多模型评审及人工自审

- 开发模型、评审模型分别配置，支持多个评审任务。
- 评审输入包括需求、验收标准、方案、代码差异、必要上下文、验证结果及约束。
- 记录问题位置、严重程度、触发条件、影响、依据、建议、状态和处理原因。
- 问题状态包括待处理、已修复、待复审、已接受风险、不采纳。
- 模型意见冲突由开发者裁定；不要求所有模型意见都被采纳。
- 评审结论绑定代码基线；代码变化后标记适用性并重跑必要评审。
- 开发者可查看完整差异并通过或退回自审。

### FR-07 文档和测试材料

概要设计至少包含需求背景、改动范围、模块职责、业务流程、接口及数据变化、数据库/消息/缓存依赖、异常处理、兼容性、性能考虑、迁移与回退、验证结果、风险和待确认项。

测试单至少包含用例标识、需求关联、环境和数据、前置条件、操作步骤、预期结果、异常与边界、权限场景、回归和联调范围、实际结果及关联问题。

性能测试单按需生成，包含场景、负载、数据规模、环境、指标和通过标准。Agent 可建议是否需要性能测试并说明理由；缺少指标时不得自行认定验收标准。

- 模板可配置，产物可人工编辑、版本保存及 Markdown 导出。
- 每个产物记录需求版本、代码基线、生成方式和来源。
- 人工编辑保留为新版本，重新生成不能静默覆盖。
- 严格区分测试材料生成、测试执行及测试通过。
- 主管评审支持手工登记结论及评审附件。

### FR-08 反馈与变更闭环

| 类型 | 处理规则 |
| --- | --- |
| 测试 Bug | 保存复现、预期/实际结果，修复后复评和复测 |
| 需求变更 | 形成新需求版本，重新分析范围、方案和验收标准 |
| 架构变更 | 更新方案和项目依赖，必要时先评审后开发 |

- 问题关联原需求、项目、代码及产物，保留处理历史。
- 变更后识别并标记受影响的任务、评审、文档和测试。
- 过期结果不能作为当前需求版本的完成依据。

### FR-09 交付与归档

- 导出各项目代码差异、版本清单、分析、设计、测试结果、评审记录和遗留问题。
- 归档后保留追溯信息，支持停止运行资源与按策略清理。
- 推送远程分支、创建 PR 和生产发布不作为第一版自动执行动作。

## 6. 状态与控制规则

业务阶段与运行状态分别记录。

- 业务阶段：接收、分析、范围确认、开发、模型评审、自审、设计评审、测试准备、测试反馈、可交付、归档。
- 运行状态：未开始、排队、运行、等待人工、暂停、失败、完成、取消。

规则：

1. 前置条件未满足时不得执行依赖步骤。
2. 单项目失败可不影响无依赖任务。
3. 取消保留已有改动，取消不等于代码回滚。
4. 重试说明沿用当前工作区还是恢复到指定检查点。
5. 需求或方案退回时创建修改记录并返回相应步骤。
6. 存在阻塞问题或必要检查未完成时不得交付。

## 7. 页面需求

| 页面 | 内容 |
| --- | --- |
| 首页 | 需求列表、阶段、状态、待处理事项、资源占用 |
| 需求详情 | 需求版本、项目、流程、执行、问题及产物 |
| 项目与环境 | Dockerfile、配置、挂载、端口、依赖、操作及日志 |
| 执行详情 | 输入、模型、事件、日志、结果及取消/重试 |
| 代码评审 | 代码差异、模型及人工意见、处理和复审 |
| 文档中心 | 各类产物、版本、适用性和导出 |
| 配置中心 | 项目模板、流程、模型、Agent、文档模板及敏感配置引用 |

关键步骤应说明目的、需要确认的事项、已知风险和建议下一步，帮助熟悉新项目。

## 8. 非功能需求

| 编号 | 要求 |
| --- | --- |
| NFR-01 可追溯 | 产物可关联需求版本、代码基线、配置、工具、模型和时间 |
| NFR-02 可恢复 | 服务重启后保留状态，核实中断执行，不盲目重复有副作用操作 |
| NFR-03 可观测 | 按需求、项目、执行查询日志，错误可定位具体阶段 |
| NFR-04 可控 | 有并发及资源限制，支持排队、取消和清理 |
| NFR-05 敏感信息 | 凭据按需注入，不写入镜像、仓库、文档及普通日志 |
| NFR-06 可扩展 | 流程、执行工具、模型、环境和文档模板可独立调整 |
| NFR-07 可移植 | 环境配置可复用，代码及产物可导出 |

## 9. 范围分期

| 分期 | 范围 |
| --- | --- |
| P0 / MVP | 需求、项目、代码副本、Docker、OpenCode、默认流程、人工确认、多模型评审、文档、反馈及导出 |
| P1 | 更完整的流程配置、跨项目自动调度和联调、自动测试接入、知识沉淀、成本统计 |
| P2 | 多人协作、在线审批、外部需求平台、自动创建 PR、团队模板 |

MVP 可拆成多个可运行迭代。第一迭代先打通需求创建、环境创建、Agent 执行、日志/差异和人工确认；不能将这一迭代误认为整个 MVP 已交付。

## 10. 验收标准

| 编号 | 场景与通过标准 |
| --- | --- |
| AC-01 | 同项目两个需求的代码、容器、会话、可写数据互不覆盖，原始目录不被自动修改 |
| AC-02 | 跨项目需求可分别执行并汇总，必要项目未完成时不得交付 |
| AC-03 | 分析列出涉及项目、改动位置、依据和待确认事项 |
| AC-04 | 按流程调用 OpenCode，保存日志、产物及人工确认结果 |
| AC-05 | 支持不同评审模型，问题可处理和复审，结论绑定代码版本 |
| AC-06 | 设计、测试材料可导出并注明版本；生成材料不会显示为测试通过 |
| AC-07 | Bug 可走完修复、复评和复测；需求/设计变更有版本历史 |
| AC-08 | 变更标记相关失效结果，阻止使用过期结论交付 |
| AC-09 | 重建容器保留代码及必要产物；中断后可定位状态和恢复处理 |
| AC-10 | 导出包含各项目差异、版本、材料、验证和遗留问题 |

## 11. 待确认项

以下信息影响落地参数，不阻塞当前整体设计：

1. 本机操作系统、CPU 架构和实际部署位置。
2. 业务项目语言、构建/启动/测试命令、仓库和依赖数量。
3. OpenCode、Superpowers 版本、调用习惯及已有配置。
4. 模型服务类型及凭据引用方式；无需在文档中提供密钥。
5. 交付采用差异导出、独立分支还是后续创建 PR。
6. 主管和测试反馈是否先采用线下评审与人工登记。
7. 自动测试及性能测试执行纳入哪个迭代。

本文的个人使用、单机优先及线下评审是设计默认值，实际选择可按用户反馈调整。
