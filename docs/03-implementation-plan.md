# 实施计划与需求追踪

- 版本：V0.1
- 日期：2026-10-24
- 依据：[需求文档](01-requirements.md)、[整体设计](02-overall-design.md)
- 当前状态：M1—M9 已合并。M10 的完整样例验收工具、固定测试和证据核对进入评审；工具演练通过，但实际模型域名被代理 403 阻断，完整在线验收保持未完成。见 [M10 操作说明](22-m10-acceptance.md) 及 [MVP 验收剩余项](13-m5-validation.md)

## 1. 实施原则

先完成 OpenCode 与 Docker 的真实执行验证，再围绕稳定的执行协议增加业务流程。每个迭代都应能独立演示，最终共同满足 P0/MVP，不将早期演示版本当成完整交付。

实际技术栈暂按整体设计中的参考方案；已有熟悉技术栈时可替换业务实现，保留执行、状态和版本边界。

M2 已落地 W01—W05 的单机基础。M3 在此基础上实现单项目的需求版本、固定步骤、范围确认、独立多模型评审、问题处置、自审及保守失效。当前仍使用明确点击推进的固定模板，不自动重试模型。在线多模型链路、用户真实项目及后续材料依赖仍需验收。

M4 接入独立材料轮次：概要设计版本与人工修订、主管登记、三态性能判断、功能/条件性能测试单、逐项实际结果登记、材料阶段验收、反馈返回及 ZIP 导出。材料与任务结果在同一事务提交；SQLite 使用显式短事务，PostgreSQL 按需求统一锁顺序。M5 继续处理跨项目汇总、完整交付、资源清理及备份恢复，不把材料阶段验收当作全项目交付。

M5 首轮实现以一个交付组关联各项目现有需求，固定整体范围与联调基线，采集时预留并停止全部成员；加入完整代码和历史交付、归档重开、任务/容器上限、按目录核实孤儿资源及全新目录备份恢复。受控双项目、真实容器和恢复演练已通过；完整 MVP 仍需按 AC-01 至 AC-10 完成用户项目试点，不能用受控登记替代实际业务评审和测试。

| M1 技术验证 | 项目副本、容器、OpenCode、插件、日志、中止及双需求隔离 | 用小需求运行一次真实修改 | 记录固定工具版本、结果及失败处理，不依赖界面完成 |
| M2 首个可运行版本 | 项目登记、需求、环境、执行、日志/差异、人工确认 | 页面完成创建需求到检查代码 | 可创建两套独立需求，持久记录和查看结果 |
| M3 默认流程与评审 | 步骤引擎、版本、范围确认、多模型、自审、失效 | 跑通分析到自审 | 固定审查基线，代码变化使旧结论失效 |
| M4 材料与反馈闭环 | 概要设计、主管登记、测试单、条件性能单、Bug/变更 | 跑通开发到测试反馈及导出 | 生成与执行分开，变更后更新相关结果 |
| M5 MVP 汇总验收 | 跨项目关联与汇总、交付、恢复、资源及清理 | 真实需求完整演练 | AC-01 至 AC-10 均有验收记录 |
| M6 项目接入与试点准备 | 运行配置版本、环境预检、样例构建测试 | 用自定义镜像和固定配置运行样例 | 样例通过不代替 M5 的真实业务验收 |
| M7 业务依赖隔离 | PostgreSQL 独立网络、数据卷、生命周期及快照 | 双需求实际 SQL 与新目录数据恢复 | 不接管共享生产依赖，样例数据可独立保存和恢复 |
| M8 应用运行与冒烟检查 | 固定应用命令、独立容器、日志及 HTTP 检查 | 双需求同端口实际应用响应，停止和恢复可追溯 | 不以健康检查替代业务测试，不自动重启不明执行 |
| M9 跨项目全景分析 | 固定候选代码集合、联合只读会话、报告与范围绑定 | 一个容器读取全部候选副本，环境检查和分析结论分开 | 不自动确认范围，报告引用代码证据；模型语义质量仍需在线验收 |
| M10 完整样例验收 | 固定独立测试、逐步推进、人工门禁、模型与反馈证据 | 本机可继续运行的样例与缺口清单 | 需真实在线开发、双模型评审、人工登记及反馈复测；当前在线阻断，尚未完成 |

M5 的跨项目执行可先固定流程加人工控制顺序。动态依赖推断、自动跨项目调度和自动联调属于后续增强。

## 3. M1 技术验证清单

### T01 选择试点并固定环境

- 输入：一个可运行的后端项目、一个小需求、现有 OpenCode/Superpowers 使用方式。
- 工作：记录系统架构、源代码基线、构建/启动/检查命令和依赖；锁定工具版本。
- 产出：试点清单、最小项目配置、初始化诊断。
- 验收：能够说明实际运行的工具、版本和代码，不依赖未记录的本机配置。

### T02 创建独立源码与容器

- 工作：复制为独立仓库，纳入选定的未提交代码；构建、启动和停止环境。
- 产出：来源清单、工作区快照、容器/卷/网络清单。
- 验收：修改不影响原始目录；重建环境后代码保留；敏感文件没有被意外复制。

### T03 OpenCode HTTP 能力探测

- 工作：健康检查、创建会话、提交简单任务、事件订阅、查询状态、收集输出。
- 产出：固定版本能力报告及一次成功/失败运行记录。
- 验收：能区分已接收、运行、等待输入、成功和失败；断开浏览器不导致任务丢失。
- 兼容：若实际版本的 HTTP 不满足需求，验证 CLI 适配，不在业务层散布版本判断。

### T04 Superpowers 与授权验证

- 工作：验证插件安装、技能可用、计划和实施产物；检查容器内命令授权。
- 产出：锁定插件版本和配置格式，记录哪些能力可自动执行。
- 验收：技能实际加载，代码和验证产物可采集；业务确认不会被技能内部回复绕过。

### T05 中止、重启及状态核实

- 工作：执行中请求取消、终止控制进程、重启 Runner、模拟事件连接断开。
- 产出：会话定位记录、中断核实流程、残留差异。
- 验收：旧执行未确认停止前不启动第二个写入者；未知状态不自动重发代码修改。

### T06 双需求隔离

- 工作：同一项目运行两个不同需求，并分别产生代码变化及测试数据。
- 产出：代码、端口、卷、网络和会话对照记录。
- 验收：原目录和另一需求不变；关闭一个环境不影响另一个；数据不串用。

### T07 评审快照与凭据边界

- 工作：生成固定代码快照，使用独立模型会话评审；开发继续变化后对比评审基线。
- 产出：审查快照摘要、模型标识、评审结果和脱敏日志样本。
- 验收：不同评审读到相同代码，正式产物不能被 Agent 直接覆盖，日志不暴露凭据。

M1 使用真实模型前再按接入方式处理凭据。文档阶段不要求用户提供明文密钥。

## 6. 必要验证场景

实现阶段围绕高风险状态和跨边界行为验证，不为静态文档或简单展示添加重复测试。

1. 同一执行请求重复点击只创建一个业务意图。
2. Runner 在请求接收前后中断，恢复后不盲目重复执行。
3. 租约过期后旧执行仍存活时，新执行不能同时写工作区。
4. 中止请求已返回，但任务仍活动时，写锁不释放。
5. 仅 HEAD 相同、未提交文件变化时，原评审仍被识别为过期。
6. 自审/主管确认后代码或文档变化，确认结果不能自动沿用。
7. 性能测试状态未决时不默认为无需执行。
8. 测试材料已生成、尚无执行记录时，不能显示测试通过。
9. 单个项目已完成、另一必要项目失败时，整个需求不能交付。
10. Agent 输出包含越界路径或符号链接时，收集操作不会覆盖正式存储或宿主文件。
11. 容器重建保留代码；删除运行资源不误删仍需保留的数据。
12. 上游事件无法回放时，界面说明缺口，不伪造完整日志。

## 7. 风险、取舍和后续演进

| 风险或限制 | 当前处理 | 后续演进 |
| --- | --- | --- |
| OpenCode 版本接口差异 | 固定版本、能力探测、单独适配器 | 扩展兼容矩阵 |
| 用户项目依赖复杂 | 先选择小项目，形成环境模板 | 复用模板及自动诊断 |
| 多需求占用资源 | 并发限制、排队和用量展示 | 远程 Runner 及多机分配 |
| 同项目合并冲突 | 独立分支、交付前比较及验证 | 辅助冲突处理 |
| 自动流程修复循环 | 次数上限和人工处理 | 按失败类别细化策略 |
| 安全边界被误解 | 区分容器权限、宿主权限和真实网络执行状态 | 独立虚拟机执行环境 |
| 文档和代码不一致 | 基线绑定及保守失效 | 按模块细化依赖 |
