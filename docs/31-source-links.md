# 源码链接与导出

工作区从 Git 已提交的 HEAD 导出源码，不直接复制宿主目录。多仓库项目的父目录不需要初始化 Git，每个选中的子仓库分别导出。报错 `Unsupported archived entry: .harness` 通常说明某个子仓库把 `.harness` 提交为符号链接，而旧版本只允许普通文件。

## `.harness` 直接复制

`.harness` 按 Git 中的原始内容复制，不解释配置、不检查其链接目标，也不递归展开目标目录。具体规则：

- 普通文件保留该提交中的原始内容；普通目录复制已提交的文件，不解析配置内容。
- `.harness` 本身或其目录下的条目若是 Git 符号链接（模式 `120000`），直接读取该条目的 Git blob，原始目标路径文本保存为普通文件（模式 `100644`）。不创建系统链接，不改变原项目。
- 目标缺失、指向仓库外、绝对路径或指向自身，都不影响该链接文件的复制。目标内容不会因此进入工作区。
- 原有凭据排除规则与导出容量限制继续适用。直接复制记录保存在私有 `workspace.json` 的 `copied_link_files` 中，多仓库按子仓库记录。

例如 `.harness -> ../local-config` 会得到内容为 `../local-config` 的普通文件 `.harness`，不会生成同名配置目录。Windows 不需要开启开发者模式或授予创建链接权限；目标文本也不会被本机路径规则当作需要访问的目录。

此规则用于新导出的工作区，不会把已有工作区中的目录自动改写为文件。如运行工具确实需要外部配置目录，可通过项目运行配置挂载接入。

## 支持的链接

除上述 `.harness` 规则外，其他已提交的相对链接，只要目标在同一仓库已提交且未被排除的内容中，就会展开为普通文件或目录。支持文件链接、目录链接、链接链、内部 `../` 相对目标和目录中的链接；按实际链接关系处理路径，不从宿主文件系统读取目标。

例如 `source-link -> tools/shared` 会在独立副本中生成普通目录 `source-link`，其中保存该提交中 `tools/shared` 的内容。两个位置在副本中分别独立，原项目也不受影响。新工作区的私有 `workspace.json` 记录展开链接映射；多仓库工作区按子仓库记录。

Windows 无需开启开发者模式或授予创建符号链接权限；即使原检出使用 `core.symlinks=false` 并把链接检出为目标路径文本，也会依据 Git 归档中的链接类型和目标正确导出。脚本执行标记按目标文件保留。

`.env`、凭据目录、`node_modules` 等原有排除规则同时应用到原路径和展开后的路径，不能借链接带入。展开后的导出仍受 100 MiB 和 100000 条目限制，链接链最多 40 层。

## 不在自动展开范围的内容

其他需要展开的源码链接遇到以下情况时，会给出包含子仓库、链接名和原因的错误，不会留下可继续执行的半成品工作区。`.harness` 的目标不执行这些检查：

- 目标是绝对路径、位于该子仓库之外（包括共同父目录及其他子仓库）、未提交、已被 `export-ignore` 排除，或属于凭据排除项。
- 链接循环、目录指回自身/祖先、链接过深、目标路径不适用于当前平台，或展开后超限。

原项目包含已提交链接时，CLI 的 `--include-dirty` 脏文件叠加暂不支持；先提交改动，再按 HEAD 创建。工作台登记需求默认使用 HEAD，不受此限制。导出后的副本都是普通文件，可继续用于分析/评审副本和脏文件复制。

项目目录、共享文件、宿主挂载路径和运行过程中新增的链接仍使用原来的路径检查规则；这项兼容仅针对 Git 归档中可核对的已提交链接。外部工具配置或数据需要通过项目运行配置的挂载显式接入。

## 多仓库父目录如何排查

不要在业务父目录执行 `git init`。新版错误会显示 `复制子仓库 services/order 失败：...`，在该子仓库中运行：

```powershell
git -C .\services\order ls-tree HEAD -- .harness
```

首列 `120000` 表示已提交链接，可读取其目标：

```powershell
git -C .\services\order show HEAD:.harness
```

如果 `.harness` 只是本机工具入口且不需要进入容器，可以在这个子仓库的 **Git 本地属性文件** `.git/info/attributes` 添加一行 `.harness export-ignore`。它只影响本地导出，不改变源码提交；Git worktree 等特殊仓库布局可用 `git -C .\services\order rev-parse --path-format=absolute --git-path info/attributes` 找到属性文件的实际位置。保留该文件已有规则，不要覆盖整个文件。团队需要共同排除时，可按团队流程把同一规则加入已提交的 `.gitattributes`。

如果 Agent 或构建实际依赖目标内容，请将所需内容纳入仓库，或先排除这个宿主链接、再通过运行配置挂载到需要的位置。不要把真实凭据提交到仓库。修正后可直接在原需求的当前步骤重试创建工作区，无需重新登记父目录和需求。
