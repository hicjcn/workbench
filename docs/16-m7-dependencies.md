# M7 按需求隔离 PostgreSQL 依赖

沿用用户“先用样例完善接入能力”的范围。本轮先支持受限的 PostgreSQL 17 模板，不解析任意 Compose 文件。

每个需求工作区拥有独立容器、内部网络、命名数据卷与认证。开发容器通过私有网络获得连接参数；只读分析、评审、材料及预检副本不接入数据库，不继承数据库凭据。依赖容器计入全局容器上限，启动前按整套环境检查容量。

停止先终止开发写入，再生成逻辑快照并停止数据库；普通停止不删除数据卷。资源归属无法确认、快照失败或预期数据丢失时保守进入待核实，不自动创建空库替代已有数据。

离线备份 v2 包含经过摘要校验的数据库逻辑快照，排除依赖认证和运行记录。恢复到新目录后不自动启动；首次明确启动创建独立数据卷和新凭据、导入快照后才开放开发环境。继续支持 M5/M6 的 v1 备份。

## 运行样例

先构建固定工具镜像、准备 PostgreSQL 镜像，再构建包含固定 Node PostgreSQL 客户端的样例镜像：

```bash
docker build -t agent-workbench-m1:local poc/container
docker pull postgres:17-bookworm
docker build -t agent-workbench-postgres:local poc/postgres-sample
```

代理环境的最后一个构建命令应加 `--secret id=proxy_ca,src="$CODEX_PROXY_CERT"`，沿用现有代理和 CA，不关闭 TLS 校验。npm 客户端依赖通过 lockfile 固定，镜像不包含业务源码或数据库认证。

把 `poc/postgres-sample/source` 复制到尚不存在的独立目录，并执行 `git init`、`git add` 和首次提交；操作方式参照 [M6 样例接入](14-m6-project-onboarding.md)。然后：

1. 登记这个 Git 仓库。在“项目运行配置”选择镜像 `agent-workbench-postgres:local`，构建命令 `node --check dataset.cjs`，验证命令 `node --test dataset.test.cjs`。
2. 勾选“为每个需求启用独立 PostgreSQL 17”，保存新版本。等价的请求体见 [profile.sample.json](../poc/postgres-sample/profile.sample.json)。当前只支持此模板和一个数据库实例，不解析任意 Compose 配置。
3. 新建两个需求，分别创建工作区、执行环境预检、启动环境。新版本只影响尚未固定运行配置的工作区。
4. 每套开发环境使用两个容器名额：一个开发容器和一个数据库容器。默认上限 4 可同时运行两套；启动前按整套所需名额检查，容量不足时明确失败，先停止不用的环境再重试。
5. 执行项目验证。样例真实创建表、写入一行并读取校验；没有调用模型，也不会自动完成流程评审或材料验收。
6. 点击“停止环境”。页面显示数据库已停止、数据卷保留和最近快照摘要。再次启动使用原数据卷，不清空数据。

API 与 Runner 仍需使用相同数据目录和模型配置。只运行本机预检和样例测试时，可在两个终端统一设置 `AWB_MODEL=opencode/glm-5.3-flash-free`，避免默认 OpenRouter 启动要求凭据；这些操作不发送推理请求，也不证明免费模型在线可用。

## 连接与隔离

准备时固定 PostgreSQL 的实际镜像 ID。每个需求工作区派生不同的容器名、内部网络和命名卷，保存随机数据集标识与独立密码；数据库不发布宿主端口。依赖默认 0.5 CPU、512 MiB 内存和 128 个进程；API 支持 CPU 0.25—4、内存 256—4096 MiB、进程 64—512。网页保留已保存的限额。

开发容器获得 `PGHOST`、`PGPORT`、`PGUSER`、`PGDATABASE` 和 `PGPASSWORD` 环境变量。主机名为 `awb-postgres`，数据库和用户名为 `app`；应用使用自己的驱动读取这些变量。工作台不会把 Java/Spring 等项目自动改成读取此约定，需要在项目配置或代码中映射。

密码通过进程环境按变量名交给 Docker，不放在命令参数、公开运行配置或普通交付包。工作区私有认证文件权限为 `0600`；执行日志对工作台已知的数据库密码脱敏。业务代码自行保存或输出的任意秘密不在自动识别保证内。

分析、模型评审、材料和预检使用独立只读副本，不连接数据库网络、不继承数据库环境变量。预检报告新增这一检查；模板和挂载通过不代表实际模型行为已经验证。Agent 输入只说明可使用的配置目标、命令及连接变量名，不包含密码。

## 停止、中断与数据保护

停止先清除开发写入者（包括缺少运行记录但能核实归属的孤儿），再终止数据库内遗留业务连接，流式执行 `pg_dump`，校验并发布快照，最后移除数据库运行容器和空网络。数据卷继续保留，不执行全局 prune 或自动删除数据卷。

容器和卷同时校验控制目录、工作区路径、数据集标识和挂载关系。不能证明归属时拒绝接管或清理。检查点失败、资源停止未确认时，保留数据卷并进入 `UNKNOWN`，须从当前需求执行“停止并核实”，不能继续写工作区。

数据库被外部停止或容器缺失、但拥有的数据卷仍存在时，明确的停止/核实操作可能临时启动数据库以采集快照，然后关闭；不会启动 Agent。若运行中的数据卷意外丢失，不会自动用旧快照或空库替代，应从确认的备份恢复到新目录。

恢复导入失败时保留原始有效快照和恢复标记，不将部分导入的数据重新导出覆盖原快照。明确停止后显示“恢复未完成，待继续”；下次明确启动重试导入，成功前不开放开发环境。

## 备份和恢复

沿用 [离线维护命令](12-m5-delivery.md)，先停止 API/Runner，运行维护 `stop` 核实资源，再 `backup`。v2 备份包含每个已使用数据库的逻辑快照、数据集标识、镜像 ID、大小和 SHA-256，排除数据库密码、依赖运行记录和原始 Docker 卷目录。尚未使用的数据库不伪造数据快照。

```bash
.venv/bin/python -m agent_workbench.maintenance stop --data-dir /path/to/data
.venv/bin/python -m agent_workbench.maintenance backup --data-dir /path/to/data
.venv/bin/python -m agent_workbench.maintenance restore \
  --archive /private/path/to/backup.zip --destination /path/to/new-data
```

恢复只写入新目录，不自动创建容器。用新令牌启动恢复后的工作台，再明确启动需求环境；系统生成新数据库凭据、新卷和新网络，导入已校验的快照后启动开发容器。原目录的数据卷不会被接管。固定镜像仍需单独保存/加载；数据恢复只支持本轮 PostgreSQL 17 自定义逻辑快照。

数据库业务数据可能包含敏感内容，备份需私密保存。单个逻辑快照上限 256 MiB（导出后检查），完整归档展开大小仍为 512 MiB；这些是导出限制，不是数据库卷磁盘配额。普通交付包只增加快照摘要，不打包数据库业务数据。

本轮版本为 0.7.0；控制面 SQL schema 保持 `0006`，没有新增数据库迁移。新备份格式为 `workbench-backup/v2`，需 0.7.0 或更高版本恢复；M5/M6 的 v1 归档仍可读取。结果与未验证项见 [M7 验证报告](17-m7-validation.md)。
