# M3 默认流程与评审

- 版本：0.3.0；日期：2026-10-24。
- 基于已合并的 M1/M2，沿用持久化队列、单机 Runner、OpenCode 和既有 Docker 镜像。
- 范围：单需求、单项目；跨项目展开及 M4 文档闭环后续推进。在线多模型串联仍待验收。

## 固定流程 v1

只读分析 → 范围确认 → Superpowers 开发 → 实际验证命令 → 不同模型独立评审 → 问题处理确认 → 开发者自审。

每次只由用户明确启动下一步，不自动重试模型任务。人工确认和模型报告分别保存，不把模型完成等同于人工通过。

## 本机使用

安装、构建和启动方式沿用 [工作台操作说明](06-m2-workbench.md)。重启 API 自动应用 `0003` 迁移；已有 M2 需求可以保留原操作方式，手动开启流程后才启用步骤门禁。

1. 登记项目、创建需求、创建工作区并启动环境。
2. 点击“开启默认流程”，填写两个不同的免费评审模型、验证命令和本轮原因。API 最多支持四个评审模型，当前表单提供两个。
3. 运行只读分析，检查报告后填写依据并确认范围。分析只覆盖当前登记的项目。
4. 运行开发步骤。输入包带入已确认的需求、方案和上游结果，并要求使用已安装的 Superpowers。
5. 执行验证命令。Runner 直接在需求容器中执行参数列表，检查实际退出码；不使用宿主机 shell。命令退出 0 仅表示该命令完成，仍需判断测试覆盖和业务验收。
6. 分别运行评审模型。每个模型使用独立容器、Agent 主目录和只读源码；第二个模型不会接收第一个模型的结论。
7. 对每个 BLOCKER/MAJOR 问题记录接受风险或确认误报的依据，再确认问题处理、自审。需要修复代码时退回本轮，修改后重新开启并评审。
8. 修改需求使用“修订需求”；“流程历史”可以查看先前轮次的报告及确认记录。

分析/开发模型由 API 与 Runner 的 `AWB_MODEL` 决定，沿用 M1 默认值。评审模型可以选择显式的 `opencode/*-free`、`opencode/big-pickle` 或 `openrouter/vendor/model:free`。OpenRouter 读取既有 `OPENROUTER_API_KEY`，执行前核实公开目录价格；不提供付费回退。服务商目录中存在模型不保证额度或调用可用。

单个模型报告最多 80,000 字符，必须符合对应 JSON 结构。技能宣告和工具进度保留在日志，最终文本作为报告解析。格式不合格时保留失败及代码，不自动补发模型请求。

## 版本和失效

- 需求正文保存不可变修订，更新时校验预期版本。
- 每轮保存需求版本、代码摘要、模型、验证命令、固定模板版本及每步输入摘要。
- 分析及评审只挂载独立快照副本，源码只读，不共享开发 Agent 主目录。
- 每个评审读取相同代码摘要；问题使用报告及序号定位，阻断/主要问题必须逐项记录处置和原因。
- 开发完成更新本轮代码基线；其后代码变化、需求修订或重开流程均使旧结论失效，历史输入、报告和确认保留。
- 开启流程后，普通任务和旧自审接口不能绕过步骤门禁。
- UNKNOWN 继续要求停止并核实，核实范围包括只读分析/评审的独立容器。

开发本身引入的代码变化成为后续验证和评审基线；其他时点变化使本轮失效。Runner 空闲时检查当前流程的代码，即使尚未自审也会发现变化。Runner 停止时不能提供持续观察，但下一步执行前会重新核实基线。

代码、只读执行副本及私有运行记录保存在数据目录，正式输入和报告保存在控制数据库，Agent 不挂载控制数据库。副本目前保留以供追溯，自动归档清理后续提供。

## 接口和存储

| 接口 | 行为 |
| --- | --- |
| `GET /api/v1/requirements/{id}/workflow` | 当前需求修订、当前步骤、输入摘要及历史索引 |
| `POST /api/v1/requirements/{id}/workflow` | 固定模型、验证命令和代码摘要，开启新一轮 |
| `POST /api/v1/requirements/{id}/workflow/steps` | 校验前置和人工输入，在同一事务登记步骤及队列任务 |
| `POST /api/v1/requirements/{id}/revisions` | 携带预期修订 ID 保存新版正文与变更原因 |
| `GET /api/v1/requirements/{id}/workflow/runs/{flow_id}` | 查询该轮不可变输入、报告、需求版本及确认 |

迁移新增 `requirement_revisions`、`workflow_runs`、`workflow_steps`，不覆盖原 `jobs`、事件或 M2 确认记录。步骤沿用任务的租约、幂等及 UNKNOWN 核实规则。历史输入只在明确打开历史记录时返回，常规轮询不重复传输全部输入包。

## 验证目标

覆盖持久化门禁、幂等、版本并发、失效、同摘要多模型、独立会话、只读挂载、实际命令退出码、人工问题处置及恢复。真实模型验证受当前服务访问与凭据约束，受控测试明确标注，不冒充在线推理。

```bash
.venv/bin/python -m unittest discover -s tests -v
npm run --prefix web build
# 需要可选 browser 依赖、系统 Chromium 和 Docker；使用全新专用目录：
.venv/bin/python poc/verify_workflow.py --root .local-data/m3-acceptance-01
# 可选 PostgreSQL 真容器检查：
.venv/bin/python poc/verify_postgres.py --root .local-data/m3-postgres-01
```

`verify_workflow.py` 的独立验收 Runner 明确使用受控报告，未调用模型；容器、只读挂载、验证命令、API、数据库和浏览器均实际运行。生产 Runner 不使用此验收替身。当前还不能把这些检查称为真实多模型开发验收。
