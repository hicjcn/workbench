# M8 应用服务与 HTTP 检查

版本 0.8.0，控制面 schema 仍为 `0006`，无需新增 SQL 迁移。PR #7 已合并，提交 `3d51b5f27ba56e4b9d7e811475ef68e438df0722`。本阶段继续使用样例完善项目接入。

## 使用

先按 [M7 说明](16-m7-dependencies.md) 构建 PostgreSQL 客户端样例镜像，将 `poc/postgres-sample/source/` 复制到自己的样例 Git 仓库并提交。该目录新增 `server.cjs`，`GET /health` 实际查询当前需求的数据库，返回健康状态和行数。

在“项目登记 → 项目运行配置”启用“应用服务与 HTTP 检查”。[完整样例配置](../poc/postgres-sample/profile.sample.json) 可通过已有配置 API 提交，新增部分为：

```json
{
  "application": {
    "start_command": "node server.cjs",
    "port": 3000,
    "health_path": "/health",
    "expected_status": 200,
    "ready_timeout_seconds": 30
  }
}
```

这段配置位于运行配置的 `content` 内。旧配置可以没有此字段，已有需求的固定版本不会自动改变；需要新建需求采用新配置。

依次创建工作区、环境预检、启动开发环境、执行需要的构建，然后在“应用服务与 HTTP 检查”点击启动。工作台在独立应用容器运行命令，通过 `PORT` 环境变量传入端口，等待配置的路径返回预期状态。命令直接按参数执行，不通过宿主或容器 Shell 拼接；复杂步骤请写入仓库脚本。镜像须包含 Node，供固定 HTTP 探针使用。预检检查启动命令入口，但不运行应用或调用模型。

应用服务使用固定镜像 ID、CPU/内存/PID 限额和只读配置副本，另占一个容器名额，限额按容器计算。默认容器上限为 4；同时运行两套“开发 + PostgreSQL + 应用”需要在 API 与 Runner 一致设置 `AWB_MAX_CONTAINERS=6`。容量不足时启动失败，不会自动回收其他需求。

容器数和内存限额不会预留磁盘。当前云环境的 vfs 驱动会为容器复制镜像文件，六容器样例需要额外空间；可在“资源与恢复”查看剩余磁盘。本轮清理了可再生成的样例 npm 下载缓存，保留源码、会话、报告和数据库快照。

可显式执行四种任务：

| action | 行为 |
| --- | --- |
| `app_start` | 启动一次应用，等待固定 HTTP 检查；已有运行记录时拒绝重复启动 |
| `app_check` | 核实归属与代码基线后执行一次检查；不自动启动或重启服务 |
| `app_logs` | 读取最后 40 行容器日志，返回最多 16000 字符，使用已有密码脱敏机制 |
| `app_stop` | 停止应用容器，保留开发环境、数据库与最近检查历史 |

入口为 `POST /api/v1/requirements/{id}/actions`，沿用鉴权、幂等键、持久任务、租约和工作区互斥。任务日志及结果可在现有执行记录中查看。检查失败会保留应用容器与日志，也保留开发环境的状态，便于检查和明确停止后重试。

## 隔离与检查含义

应用容器以当前用户运行，根文件系统和代码挂载只读，临时目录限额，无 Docker Socket，不挂载 Agent 主目录，不注入工作台令牌或模型认证。配置中的 PostgreSQL 必须已由开发环境启动；应用只加入本需求内部数据库网络，通过 `PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSWORD` 使用独立数据集。未配置依赖时使用 Docker `none` 网络，仍可在容器内检查回环地址。

本轮没有发布应用宿主端口，也没有浏览器反向代理。不同需求可同时使用相同的容器端口。HTTP 探针通过 Docker exec 在应用容器内连接固定的 `127.0.0.1` 和配置端口，路径不接受完整 URL、查询参数或额外请求头；不跟随重定向，单次请求最多 2 秒，响应体上限 64 KiB。只记录状态码、耗时、体积和 SHA-256，不保存响应正文或头。容器日志轮转上限 1 MiB；应用主动写入日志的业务内容仍应按私有数据保管。

页面显示“上次 HTTP 检查通过”及时间。这不是持续健康监控，也不会自动完成开发流程验证、自审、主管审批或测试单。检查不会调用模型。进程退出、连接失败、超时、响应过大或状态码不符都不能通过。

启动记录绑定代码树摘要和固定配置。开发容器仍可修改自己的源码；应用的只读挂载不构成不可变快照。观察到代码摘要变化后，旧服务标为过期，检查不能通过，必须停止并重新启动应用。代码摘要沿用工作区规则，排除依赖和构建输出；它不证明被排除构建文件的内容或完整业务正确性。

## 停止、异常与恢复

普通“停止环境”、明确核实、取消后的清理、交付采集和离线维护都会先停止应用与开发写入者，再执行 PostgreSQL 快照并停止数据库。普通停止保留数据卷；单独停止应用不会采集或停止数据库。

容器使用目录、工作区、类型标签、固定镜像、无宿主端口和只读代码挂载核实归属。缺少应用运行记录时仍可识别本工作区的确定名称容器并清理。启动响应不明、容器意外消失、归属不符或停止未确认时进入待核实，不自动重发启动。使用需求的“停止并核实”，必要时停止 API/Runner 后运行已有维护命令。不能确认归属的资源保留现场。

离线备份仍用 `workbench-backup/v2`：包含运行配置、任务历史及 HTTP 检查历史，排除应用运行记录和容器原始日志。备份前必须停止并核实所有容器和运行记录。恢复到新目录后，页面将历史报告显示为已停止，必须明确启动开发环境、数据库和应用；新数据库使用新卷和重新生成的认证。仍接受原有 M5/M6 v1 和 M7 v2 归档。旧版本程序未必认识新增文件，应使用当前或更新程序恢复。

当前每个工作区只支持一个前台应用进程命令和一个 HTTP GET 检查。没有任意 Compose、多服务依赖图、应用热更新、宿主端口预览、服务间联调或压测；应用通过数据库网络访问自己的依赖，不提供通用 Internet 出口。实际业务项目和在线模型全流程仍待验收。
